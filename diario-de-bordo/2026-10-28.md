# Diário de bordo: 28/10/2026

**Tema:** Laboratório prático: ajustes com Tailwind, lacunas de lógica e o back servindo o front  
**Módulo:** Front-end (React)

## O que aprendi

- Com o Tailwind, dá para mudar o visual só trocando o nome da classe. O botão do login ficou verde trocando `bg-blue-600` por `bg-emerald-600`. Usei a mesma ideia para dar ao projeto a cara de um caderno de estudos.
- Agora o próprio servidor da API também entrega a tela do site. Assim tudo funciona num endereço só (`localhost:3000`), do jeito que vai ficar quando estiver na internet.
- Enquanto programo, uso o `localhost:5173`, que mostra as mudanças na hora. O `localhost:3000` só mostra a versão nova depois que eu gero a tela de novo com `pnpm build:web`. Era por isso que minhas mudanças "não apareciam".

## As 3 lacunas

| Lacuna | O que fiz | O que acontecia sem ela |
| --- | --- | --- |
| 1 | Fiz a tela buscar as tarefas na API, mandando junto o "crachá" do usuário logado (o token) | a lista ficava vazia e a API respondia "não autorizado" |
| 2 | Fiz a tela recusar tarefa com título em branco ou com menos de 3 letras, mostrando um aviso | dava para criar tarefa sem nome |
| 3 | Disse que o botão de trocar entre "entrar" e "criar conta" é só um botão, e não o de enviar o formulário (`type="button"`) | clicar nele enviava o formulário e recarregava a página |

## Perguntas do laboratório

**A. O que acontece se usarmos uma variável comum em vez do `useState`?**

> A tela não muda. O valor muda por dentro, mas o React não fica sabendo que precisa desenhar a tela de novo. O `useState` é o jeito de avisar o React.

**B. Por que o formulário do login recarregava a página?**

> Todo botão dentro de um formulário, por padrão, envia o formulário, e o navegador recarrega a página. Com `type="button"`, o botão só faz o que eu mandei no clique.

**C. Qual a vantagem do Tailwind em relação a um arquivo `.css`?**

> O estilo fica junto do elemento. Para mudar a aparência, eu troco a classe ali mesmo, sem procurar em outro arquivo.

**D. Preciso liberar o CORS?**

> Enquanto programo, sim: a tela (`:5173`) e a API (`:3000`) estão em endereços diferentes, e o navegador bloqueia essa conversa se a API não liberar. Quando o servidor entrega a tela, não: tudo vem do mesmo endereço.

## Problemas que apareceram

| Problema | Por que aconteceu | Como resolvi |
| --- | --- | --- |
| O terminal dizia que o `tsx` não existia | faltava instalar as dependências naquela pasta | rodar `pnpm install` na pasta |
| A tela não era gerada (erro de arquivo não encontrado) | o `index.html` original tinha sido trocado por uma cópia da versão gerada | voltar o `index.html` original e nunca editar a pasta `dist` |
| Pastas enormes (`node_modules` e `dist`) apareciam para subir no Git | o `.gitignore` tinha um espaço antes de cada linha | tirar os espaços |
| Um comentário quebrava a tela | estava dentro da tag do botão | mover o comentário para fora da tag |
| O pnpm se recusava a instalar alguns pacotes | por segurança, ele bloqueia pacotes que rodam programas na instalação | liberar só os pacotes necessários no `pnpm-workspace.yaml` |

## Como fiz o servidor entregar a tela

1. Gerei a versão final da tela com `pnpm build:web`, que cria a pasta `dist`.
2. No servidor, a ordem das peças importa. Primeiro, um endereço da API que não existe responde "não encontrado". Depois vêm os arquivos da tela. Por último, qualquer outro endereço abre a tela do React.
3. Se essa ordem fosse invertida, um endereço errado da API abriria a tela no lugar de avisar o erro.
4. Testei abrindo `localhost:3000`: a tela abriu e a API continuou respondendo.
