# Diário de bordo: 04/11/2026

**Tema:** Banco de dados em nuvem com Turso e libSQL  
**Módulo:** Back-end (API)

## O que aprendi

- Em hospedagens como Render e Railway, o disco do container é **efêmero**: a cada deploy ou reinício ele é apagado. Se a API continuasse gravando no `tarefas.db`, todos os usuários e tarefas sumiriam a cada atualização. A solução é separar a API (que roda e some) do banco (que fica guardado na nuvem).
- Trocamos o `better-sqlite3` pelo `@libsql/client`. Ele fala com o Turso pela internet quando recebe `libsql://...` e, sem credenciais, abre o arquivo local com `file:./tarefas.db`. O mesmo código serve para os dois casos.
- As credenciais (`TURSO_URL` e `TURSO_TOKEN`) ficam em `gerenciador-tarefas/api/.env`, que está no `.gitignore`. No Git vai só o `.env.example`, sem segredo.
- O SQL continua o mesmo, mas todas as consultas viraram `await db.execute({ sql, args })`. Os `?` com `args` continuam protegendo contra SQL Injection.

## As 11 lacunas

| Lacuna | O que preenchi | O que quebrava se ficasse vazia |
| --- | --- | --- |
| 1 | `import { createClient } from "@libsql/client"` no lugar do `import Database from "better-sqlite3"` | `createClient is not defined`: o servidor nem subia |
| 2 | `carregarEnv()`, que olha os 3 primeiros bytes do `.env` e avisa se houver BOM, e depois chama `process.loadEnvFile` | o `.env` não era lido, então a API nunca ia para a nuvem; e um BOM fazia a `TURSO_URL` sumir sem nenhum aviso |
| 3 | `TURSO_URL`, `TURSO_TOKEN`, `usandoNuvem` (só `true` com os dois) e `MODO_BANCO` | as lacunas 4, 5 e 9 usam essas constantes e davam `ReferenceError` |
| 4 | `const db = createClient({ url, authToken })`: Turso se houver credenciais, senão `file:./tarefas.db` | sem `db`, nenhuma rota conseguia consultar o banco |
| 5 | `exibirBannerBanco()`, que mostra modo, endereço e se o token existe (sem imprimi-lo) | o servidor funcionava, mas eu não sabia se os dados estavam indo para a nuvem ou para a minha máquina |
| 6 | `SQL_USUARIOS` e `SQL_TAREFAS`, um `CREATE TABLE` em cada constante. A senha virou `senha_hash` e as tarefas ganharam `descricao`, `criado_em` e `atualizado_em` | `inicializarBanco()` não tinha o que executar |
| 7 | `inicializarBanco()`: `db.batch([SQL_USUARIOS, SQL_TAREFAS], "write")`, `ALTER TABLE` para a coluna `atualizado_em` em bancos antigos e o usuário semente | as tabelas não existiam e toda rota dava `no such table` |
| 8 | `primeiraLinha()` e os helpers `buscarUsuarioPorEmail`, `buscarUsuarioPorId`, `inserirUsuario`, `listarTarefasDoUsuario`, `buscarTarefaPorIdEUsuario` e `deletarTarefaPorIdEUsuario` | as rotas de tarefas, que já vinham prontas, chamavam funções que não existiam |
| 9 | `/api/health`, `/api/auth/register` e `/api/auth/login` assíncronos | não dava para criar conta nem entrar, então nenhuma rota protegida podia ser testada |
| 10 | 404 em JSON para `/api/*`, `express.static`, SPA fallback e `verificarFront()` (da Aula 08) | `verificarFront is not defined` na hora de subir, e a tela não abria em `:3000` |
| 11 | `iniciarServidor()`, que faz `await inicializarBanco()` e só então chama `app.listen()` | o servidor não abria a porta. Com o `listen` direto, uma requisição podia chegar antes de a tabela existir |

## Perguntas da aula

**Por que trocamos `better-sqlite3` por `@libsql/client`?**

> Porque o `better-sqlite3` só sabe gravar num arquivo do disco, e na nuvem esse disco é apagado a cada deploy. O `@libsql/client` manda o SQL pela internet para o Turso, que guarda os dados de forma permanente, longe do container.

**Qual a diferença entre síncrono e assíncrono no banco? O que mudou nas rotas?**

> O `better-sqlite3` é síncrono: o `stmt.get()` trava o Node até o disco responder. Com o banco do outro lado da internet, a resposta demora mais, então cada consulta devolve uma Promise. As rotas viraram `async`, cada consulta ganhou `await`, `resultado.changes` virou `resultado.rowsAffected` e o `lastInsertRowid` (agora `bigint`) passa por `Number()`. Até a subida do servidor ficou assíncrona (lacuna 11).

**Qual a importância do `db.batch()`?**

> No libSQL, um `execute()` com dois comandos roda só o primeiro e ignora o resto sem dar erro. Testei: `execute("CREATE TABLE a (x); CREATE TABLE b (y);")` criou só a tabela `a`. O `batch` manda cada comando separado e é atômico: se um falhar, nenhum é aplicado.

## Erros e cuidados

| Situação | Causa | Solução |
| --- | --- | --- |
| Servidor diz "arquivo local" mesmo com `.env` preenchido | `.env` salvo com BOM | salvar em UTF-8 sem BOM. Testei com um `.env` com BOM: o aviso aparece e o modo cai para local |
| `SERVER_ERROR` com HTTP 404 | URL com `/` no final ou token cortado | conferir a URL e copiar o token inteiro |
| `PATCH` de tarefa inexistente ficava pendurado | o `server-lacunas.ts` faz `return null` sem responder | responder `404` com `res.status(404).json(...)` |
| Cadastro respondia 409 para qualquer erro | o `catch` não olhava o tipo do erro | `409` só quando o código começa com `SQLITE_CONSTRAINT`, senão `500` |
| `tarefas.db` antigo não funciona no login | a coluna era `senha` e agora é `senha_hash` | apagar o arquivo; o `CREATE TABLE IF NOT EXISTS` não altera tabela existente |
| Banner dizia "Turso", mas o health respondia "arquivo local" | um servidor antigo ainda ocupava a porta 3000. No Express 5, o callback do `app.listen` também é chamado quando a porta está ocupada, então o banner aparecia mesmo sem o servidor novo estar ouvindo | checar o `erro` no callback do `listen` e encerrar com uma mensagem clara |

## Configuração do Turso

Criei a conta com o GitHub e o banco `dsw` na região de São Paulo (`aws-sa-east-1`). Pela CLI (`brew install tursodatabase/tap/turso`, depois `turso auth login`), gerei o `.env` sem colar o token em lugar nenhum:

```bash
printf 'TURSO_URL=%s\nTURSO_TOKEN=%s\n' "$(turso db show dsw --url)" "$(turso db tokens create dsw)" > .env
```

Prova de que os dados estão na nuvem: criei uma tarefa, desliguei o servidor, apaguei o `tarefas.db` e subi de novo. A tarefa continuou lá, e o `turso db shell dsw "SELECT * FROM tarefas"` mostra a mesma linha.

Adaptações ao meu repositório: uso `pnpm` em vez de `npm`, a API fica em `gerenciador-tarefas/api` e o front em `app-react/web`. Mantive o corpo `{ email, senha }` que o front envia (o `request.http` da aula usa `password`) e a senha do admin semente como `123456`.
