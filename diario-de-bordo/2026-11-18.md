# Aula 11 — Ler, entender e melhorar o código do gerenciador para o ENADE (18/11/2026)

## ✅ O que eu aprendi

- Nesta aula o professor entregou o código pronto das telas, e o trabalho era ler e entender por que cada parte foi feita daquele jeito, antes de mudar qualquer coisa.
- Muitos erros de tela acontecem quando o código não espera o servidor responder, ou quando ele esquece um caso diferente, como uma resposta vazia.
- Se uma informação pode ser calculada a partir de outra, não vale a pena guardar as duas. Duas cópias da mesma coisa uma hora ficam diferentes.

## Etapa 1: perguntas sobre o código

### App.tsx

**1. Por que o `useState` recebe `() => getUsuario()` e não `getUsuario()`?**

> O React redesenha a tela muitas vezes, até a cada tecla digitada. Escrevendo `getUsuario()` direto, o código iria buscar e abrir o "crachá" do usuário (o token) toda vez, sem precisar. Com a setinha `() =>`, eu entrego a receita, e o React só usa ela uma vez, quando a tela abre.

**2. `logado = usuario !== null` é um estado ou uma derivação? Por que não guardar `logado` separado?**

> É uma derivação: o código descobre se a pessoa está logada olhando se existe um usuário. Se eu guardasse "logado" separado, teria que lembrar de atualizar os dois sempre. Bastaria esquecer um para a tela achar que a pessoa está logada sem ter usuário nenhum, e dar erro.

**3. Onde o token é apagado? Por que não apagar dentro do `Tarefas.tsx`?**

> No `App.tsx`, quando a pessoa clica em Sair. É o App que decide se mostra a tela de login ou a de tarefas. Se a tela de tarefas apagasse o crachá sozinha, o App não ficaria sabendo e continuaria mostrando as tarefas. Por isso a tela de tarefas só avisa "a pessoa quer sair", e quem resolve é o App.

### api.ts

**4. O `getUsuario()` lê o token na própria tela. Isso valida o token?**

> Não. O token tem três partes. A do meio, com o id e o e-mail, é só um texto codificado que qualquer pessoa consegue ler e até inventar. A parte que prova que o token é verdadeiro é a assinatura, e só o servidor tem a senha secreta (`JWT_SECRET`) para conferir. A tela usa o token só para mostrar o e-mail de quem está conectado. Se alguém inventar um token, a tela até mostra o e-mail falso, mas o servidor recusa todos os pedidos de tarefas.

**5. Por que ler a resposta como texto antes de transformar em JSON?**

> Porque nem toda resposta do servidor vem em JSON. Às vezes ela vem vazia, ou vem uma página de erro. Se eu mandasse transformar direto em JSON, o código quebraria e eu perderia o motivo real do erro. Lendo como texto primeiro, o código confere antes: se estiver vazio ou não for JSON, ele segue em frente e ainda consegue mostrar uma mensagem de erro.

**6. O endereço da API é `http://localhost:3000` enquanto programo e `""` quando o site está publicado. O que muda?**

> Enquanto programo, a tela (`localhost:5173`) e a API (`localhost:3000`) estão em endereços diferentes. Então a tela precisa do endereço completo da API, e a API precisa liberar o CORS. Quando o site está publicado, o próprio servidor entrega a tela e a API no mesmo endereço, então basta pedir `/api/tasks` e o navegador completa sozinho. Assim o mesmo código funciona em qualquer lugar.

### Tarefas.tsx

**7. Por que existem dois estados de busca (`busca` e `buscaAplicada`)?**

> Um guarda o que está escrito na caixa de busca e muda a cada letra. O outro só muda quando a pessoa para de digitar por quase meio segundo, e é ele que vai até a API. Sem isso, digitar "estudar" faria 7 pedidos ao servidor, um por letra, e as respostas podiam chegar fora de ordem.

**8. O que é `requisicaoAtual` e por que é `useRef` e não `useState`?**

> Funciona como a senha de uma fila de banco. Cada busca pega um número novo e, quando a resposta chega, o código confere se ela ainda é a última da fila. Se não for, ela é jogada fora. Assim, uma resposta atrasada não apaga a lista certa. É `useRef` porque esse número não aparece na tela: mudar ele não precisa redesenhar nada, e ele sempre tem o valor mais novo.

**9. `PRIORIDADES_PT` é um `Record<Prioridade, string>`. Se o back criar a prioridade `"urgent"`, o que acontece na compilação?**

> Depende de onde muda. Se só o servidor mudar, o TypeScript não percebe, porque ele não enxerga o servidor: tudo compila, e a tarefa aparece com a etiqueta vazia. Se eu atualizar o tipo da tarefa no `api.ts`, o TypeScript trava a compilação até eu escrever a tradução ("Urgente") e escolher a cor dela. Essa é a proteção do `Record`: ele não deixa faltar nenhuma prioridade.

### Login.tsx

**10. A senha de 6 letras só é conferida no cadastro. E se o back passar a exigir isso no login também?**

> Nada quebra, porque quem manda é o servidor. A diferença é que a pessoa só veria o erro depois de a tela ir até o servidor e voltar, e não na hora. Para continuar avisando na hora, eu teria que colocar a mesma regra no login. A conferência da tela serve para ajudar a pessoa; a do servidor serve para garantir.

**11. Por que o cadastro faz login logo em seguida, em vez de só criar a conta?**

> Porque criar a conta não devolve o crachá (o token): o servidor só responde "usuário cadastrado". Quem entrega o crachá é o login. Fazendo os dois seguidos, a pessoa já entra direto na lista de tarefas, sem digitar e-mail e senha de novo.

## Etapa 2: caça ao bug

O código que o professor mandou já veio sem os bugs, então montei cada um a partir do roteiro.

| Bug | O que muda no código | O que acontece na tela | Como corrige |
| --- | --- | --- | --- |
| A | o "Carregando..." é ligado a cada letra digitada, antes da espera da busca | a lista pisca a cada tecla. E se eu digitar uma letra e apagar, a busca não acontece e o "Carregando..." nunca mais some | ligar o "Carregando..." só depois da espera, quando a busca vai mesmo acontecer |
| B | a tela não espera o servidor salvar a tarefa como concluída (falta o `await`) | a tela recarrega a lista antes de o servidor salvar, e a tarefa continua aparecendo como pendente. Se der erro, ninguém fica sabendo | voltar o `await`, que quer dizer "espera o servidor terminar" |
| C | some a conferência de resposta vazia | quando o servidor responde sem nada, a função finge que devolveu uma tarefa | voltar a conferência |

**O que os três têm em comum:** código que não espera o servidor (B), tela mudando na hora errada (A) e um caso diferente esquecido (C).

## Etapa 3: filtro por prioridade

- Coloquei os botões "Todas / Baixa / Média / Alta" em cima da lista. O botão escolhido fica com a cor da prioridade.
- O filtro não vai até o servidor: ele só esconde, na tela, as tarefas que já chegaram. A busca por título continua indo ao servidor, e os dois funcionam juntos.
- Se nenhuma tarefa tiver a prioridade escolhida, aparece um aviso e um botão "Mostrar todas".

**Por que `useMemo` e não `useEffect` + `setState`?**

> A lista filtrada é só uma conta feita em cima da lista que eu já tenho, então não precisa ser um estado novo. O `useEffect` serve para conversar com coisas de fora do React, como a API. Usando ele aqui, a tela desenharia duas vezes (uma com a lista velha e outra com a nova) e eu teria duas listas para manter iguais. O `useMemo` faz a conta na hora e só refaz quando a lista ou o filtro mudam.

## Etapa 4: reflexão

**"O `api.ts` centraliza todas as chamadas HTTP. Cite três vantagens, um risco se a aplicação crescer muito e uma melhoria."**

> **Vantagens.**
> 1. Tudo que fala com o servidor está num lugar só. Se o endereço da API mudar, troco uma linha e as telas continuam iguais.
> 2. Todo erro é tratado do mesmo jeito. As telas sempre recebem os dados ou uma mensagem de erro pronta, sem repetir a mesma conferência em cada uma.
> 3. Cada parte cuida do seu trabalho: as telas só cuidam do que aparece, e não precisam saber como o token é enviado nem como o pedido é montado.
>
> **Risco.** Se o sistema crescer muito (usuários, projetos, comentários...), esse arquivo vira um "arquivão" onde tudo se mistura, e qualquer mudança mexe nele. Também fica fácil ele descrever o servidor errado sem ninguém notar. No código do professor isso já acontece em pequeno: o arquivo diz que o cadastro devolve `{ id, email }`, mas o servidor devolve `{ message, user }`. E cada tela ainda precisa controlar sozinha o "Carregando..." e as respostas atrasadas.
>
> **Melhoria.** Separar em partes: uma só para enviar os pedidos (já com o token), um arquivo para cada assunto (tarefas, login) e uma biblioteca como o **TanStack Query**, que já cuida do "Carregando...", guarda as respostas e descarta as atrasadas. Isso é *separation of concerns*: cada parte tem uma responsabilidade só. E melhora a *testability* (a facilidade de testar): dá para testar cada parte com um servidor de mentira, sem precisar da API ligada.

## Como testei

1. Liguei a API com um banco temporário na minha máquina, sem mexer no Turso, e a tela com `pnpm dev`.
2. Criei uma conta e 4 tarefas, e cliquei em cada botão do filtro: apareceram 1, 1, 2 e 4 tarefas.
3. Juntei o filtro "Alta" com a busca "entregar" e apareceu só uma. No "Baixa", apareceu o aviso de lista vazia.
4. Concluí uma tarefa e excluí outra, sem nenhum erro.
