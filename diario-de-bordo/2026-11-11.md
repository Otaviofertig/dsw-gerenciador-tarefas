# Aula 10 — Deploy no Render: colocar o sistema na internet (11/11/2026)

## ✅ O que eu aprendi

- Fazer deploy é colocar o sistema num endereço da internet que qualquer pessoa consegue abrir. Até agora ele só rodava na minha máquina.
- O Render pega o código do GitHub, instala tudo numa máquina dele e liga o servidor. Toda vez que eu mando um commit para a `main`, ele faz isso de novo sozinho.
- Os dados continuam no Turso. Por isso nada se perde quando o Render reinicia ou atualiza o servidor.
- As senhas (do Turso e do JWT) não vão para o GitHub. Elas ficam guardadas no painel do Render, nas variáveis de ambiente.
- Para o professor conseguir avaliar com os mesmos comandos do roteiro, juntei o projeto numa pasta só: a API na raiz e a tela em `web/`, usando npm.

## 🧩 Principal dificuldade

Os comandos do roteiro do deploy não funcionavam direto no meu projeto.

## 🔧 Como eu resolvi

O roteiro foi feito para um projeto numa pasta só e com npm, e o meu estava dividido em duas pastas e usava pnpm. Juntei tudo: a API na raiz, a tela em `web/`, e troquei o pnpm pelo npm. Antes de subir, simulei o Render numa pasta limpa, e o build passou.

## 💡 Observações

Outros problemas que apareceram nesta aula:

| Problema | Por que aconteceu | Como resolvi |
| --- | --- | --- |
| O roteiro usa npm, e o meu projeto usava pnpm | cada gerenciador de pacotes tem o seu arquivo de versões (`pnpm-lock.yaml` × `package-lock.json`) | troquei para npm e gerei os `package-lock.json` |
| O npm avisou que bloqueou um programa de instalação do `esbuild` | por segurança, o npm novo só roda esses programas se o pacote for liberado | liberei só o `esbuild` no `package.json` (`allowScripts`), igual ao material do professor |
| Os trabalhos de outras aulas misturavam com o projeto | o primeiro app React e os exercícios de Tailwind ficavam na raiz | movi para a pasta `extras/` |

## As 3 alterações no código

| Arquivo | O que fiz | O que acontecia sem ela |
| --- | --- | --- |
| `package.json` | fiz o `build` instalar as dependências do front antes de gerar a tela | no Render, o Vite não existiria e o build quebraria |
| `server.ts` | criei a rota `/api/db-check`, que mostra as tabelas e quantas linhas cada uma tem | eu não teria um jeito rápido de saber se o site publicado está mesmo ligado ao Turso |
| `render.yaml` (novo) | escrevi a "receita" do deploy: nome, plano grátis, comandos e variáveis | eu teria que digitar tudo à mão no painel, e um erro de digitação quebraria o deploy |

## Perguntas da aula

**1. Por que o `build` precisou instalar as dependências do front antes de gerar a tela?**

> Porque a máquina do Render começa vazia. Na minha máquina, a pasta do front já tinha tudo instalado, então o build funcionava. No Render não: sem instalar antes, as ferramentas que montam a tela (Vite e TypeScript) não existem lá, e o build quebra.

**2. Para que serve o `render.yaml`, e por que o `buildCommand` e o `startCommand` precisam de atenção?**

> O `render.yaml` é a receita do deploy: diz ao Render o nome do serviço, o plano, os comandos e as variáveis. O `buildCommand` prepara o sistema (instala e gera a tela) e o `startCommand` liga o servidor. Se o comando de build for só `npm install`, a tela nunca é gerada e o site abre com o aviso "Ainda não existe o build do front-end". Esse é o erro mais fácil de cometer, porque o padrão do Render é justamente só o `npm install`.

**3. Por que o `JWT_SECRET` pôde ficar em branco, e o `TURSO_URL` e o `TURSO_TOKEN` não?**

> O `JWT_SECRET` é só uma senha que o servidor usa para assinar os logins. Ela pode ser qualquer coisa difícil de adivinhar, então o Render gera uma sozinho (`generateValue: true`). Já o endereço e o token do Turso apontam para o **meu** banco. O Render não tem como adivinhar, então eu precisei copiar do Turso e colar no painel.

**4. Para que serve a rota `/api/db-check`, e o que ela confirma em produção?**

> Ela confere o banco de verdade: lista as tabelas que existem e quantas linhas cada uma tem. Em produção, ela confirma três coisas: que o servidor consegue falar com o Turso, que as tabelas `usuarios` e `tarefas` foram criadas, e quantos usuários e tarefas já existem. Ela só lê, não muda nada no banco.

**5. Por que rodar o `build` na minha máquina antes do `git push`?**

> Porque o push na `main` já dispara o deploy. Se o build estiver quebrado, eu só descubro minutos depois, lendo os logs do Render, e o site pode ficar fora do ar. Rodando antes, eu acho o erro na hora, na minha máquina, e só subo o que funciona.

**6. O que aconteceu ao apertar F5 numa página interna (como `/tarefas`)?**

> A página abriu normalmente, sem erro 404. Isso acontece porque o servidor tem uma regra no final: qualquer endereço que não seja da API recebe a tela do React, e o React decide o que mostrar. Era o resultado esperado.

**7. Encontrei algum erro? Qual foi a causa e o que fiz?**

> O roteiro do professor foi feito para um projeto com tudo numa pasta só e com npm. O meu estava dividido em duas pastas (`gerenciador-tarefas/api` e `app-react/web`) e usava pnpm, então os comandos do roteiro não funcionavam direto. Resolvi juntando o projeto: a API foi para a raiz, a tela para `web/` e troquei o pnpm pelo npm. Assim o `render.yaml` ficou igual ao do roteiro. Antes de subir, simulei o Render numa pasta limpa, sem nada instalado e sem o `.env`, e o build passou.

## Como testei

1. Copiei o projeto para uma pasta limpa, sem nada instalado e sem o `.env`, igual ao que o Render recebe do GitHub.
2. Rodei o mesmo comando de build do `render.yaml`: instalou tudo, gerou a tela e conferiu os tipos sem erro.
3. Liguei com `npm start` e testei: `/api/health` respondeu 200, o `/api/db-check` mostrou as tabelas `usuarios` e `tarefas`, o F5 em `/tarefas` abriu a tela e o login do admin funcionou.
4. Depois do deploy, é só repetir os mesmos testes no endereço do Render (estão no fim do `requests.http`).
